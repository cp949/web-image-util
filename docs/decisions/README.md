# 아키텍처 결정 기록(ADR)

이 폴더는 되돌리기 비용이 큰 설계 결정을 기록한다. 파일명은 `ADR-XXXX-<slug>.md`이고 번호는
기존 최대 번호 다음을 쓴다.

## 템플릿

```markdown
# ADR-XXXX: <제목>

## 상태

Proposed | Accepted | Deprecated | Superseded by ADR-YYYY

## 배경

- 이 결정이 필요했던 상황, 제약, 문제.

## 결정

1. 무엇을 하기로 했는가(번호 목록).

## 근거

- 왜 그렇게 결정했는가. 검토한 대안과 트레이드오프.

## 영향

- 다른 ADR과의 관계, 이 결정이 건드리는 범위.
- 구현이 끝났다면 담당 모듈/계층을 개념 단위로만 서술한다(예: "size-budget 검사를 소유하는
  모듈"). 구체적 파일 경로(`src/core/xxx.internal.ts` 등)는 적지 않는다.
```

## 불변 대상과 갱신 대상

- **불변**: "배경"/"결정"/"근거". 그 시점에 왜 그렇게 판단했는지의 기록이라 나중에 틀렸다고
  밝혀져도 본문을 고쳐 쓰지 않는다. 판단이 뒤집히면 새 ADR을 작성하고 이전 문서의 "상태"를
  `Superseded by ADR-YYYY`로 바꾼다.
- **갱신 가능**: "상태" 필드뿐이다(라이프사이클 반영: Proposed → Accepted → Deprecated/Superseded).
  구현 완료·병합 여부는 상태 필드가 다루지 않는다 — 그건 git 이력과 코드 자체가 answer다.
- **부분 대체 표기**: 새 ADR이 이전 ADR의 결정 항목 일부만 뒤집고 나머지는 유효하면, 상태를
  `Superseded by ADR-YYYY (결정 N에 한함)`처럼 범위를 괄호로 명시한다. 상태 필드만 보고 문서
  전체가 무효화됐다고 오독하는 것을 막는다.
- **애초에 적지 않는다**: "영향" 절의 구체적 파일 경로. 리팩토링마다 stale해지는데 ADR은
  그때그때 갱신하는 문서가 아니다. 담당 모듈/계층을 개념 단위로만 서술해 갱신할 필요 자체를
  없앤다. 클래스·함수·타입 이름 중에서도 공개 API 표면(사용자가 실제로 쓰는 이름)은 결정의
  본질이라 남기지만, 내부 구현 파일·클래스.메서드 참조는 남기지 않는다.

## 설계 로그와의 관계

대안 비교, 질의응답 로그 같은 상세한 설계 검토는 이 폴더가 아니라 저장소 추적 대상 밖의
작업 문서에 남기고, 완료 후 보관할 가치가 있다고 판단되면 요약만 이 폴더에 ADR로 남긴다.
ADR은 "무엇을, 왜" 결정했는지 git 이력만 보고 파악할 수 있는 최소 요약이어야 한다.
